# LAB Switch: MAC Address Table, ARP และ Collision Domain

ทดลองเดิมกับตอนใช้ Hub แต่เปลี่ยนเป็น **Switch**: ให้ PC5 ping PC8 แล้วดูว่าใครได้รับ traffic บ้าง

## ผลสำคัญ

| ข้อความ                  | ใครได้รับ        |
| ------------------------ | ---------------- |
| ARP Request (Broadcast)  | PC6, PC7 และ PC8 |
| ARP Reply กลับ PC5       | เฉพาะ PC5        |
| ICMP Echo Request ไป PC8 | เฉพาะ PC8        |

**จุดที่ต้องเข้าใจ:** ตอนเริ่ม Switch มี MAC Address Table **ว่าง** แต่ระหว่างรับส่งมันเรียนรู้เพิ่มได้ ตารางจึงไม่ได้ว่างค้างตลอดการทดลอง

---

## 1. ตารางสองตัวที่ทำหน้าที่ต่างกัน

| อยู่ที่ไหน | ตาราง             | ใช้รู้อะไร                                 |
| ---------- | ----------------- | ------------------------------------------ |
| PC5        | ARP Cache         | IP ที่ต้องการติดต่อ ตรงกับ **MAC** อะไร    |
| Switch     | MAC Address Table | MAC ที่ต้องการส่งถึง อยู่ทาง **พอร์ต** ไหน |

```text
PC5    : "รู้ IP ของ PC8 แล้ว แต่ MAC ของ PC8 คืออะไร?"
Switch : "ถ้าต้องส่งถึง MAC นี้ ต้องออกพอร์ตไหน?"
```

## 2. สถานะเริ่มต้น

- PC5 มี **ARP Cache ว่าง** จึงต้องส่ง ARP Request เพื่อหา MAC ของ PC8
- Switch มี **MAC Address Table ว่าง** คือยังไม่รู้ว่า MAC แต่ละเครื่องอยู่ทางพอร์ตไหน

ตรวจตารางบน Switch:

```cisco
show mac address-table
```

ให้ดูว่ามีรายการ MAC กับพอร์ตแล้วหรือยัง ไม่ต้องจำค่า MAC จริงในวิดีโอ

## 3. PC5 ส่ง ARP Request ก่อน ICMP

เหตุผลเหมือนฝั่ง Hub: PC5 รู้ IP ปลายทาง แต่ยังไม่รู้ MAC ของ PC8 จึงต้องถามหา MAC ก่อน

ARP Request มีข้อมูลสำคัญสองส่วน:

```text
Ethernet Frame
  MAC ต้นทาง   = PC5
  MAC ปลายทาง = FF:FF:FF:FF:FF:FF  → Broadcast

ARP Message (ข้างใน)
  "ใครใช้ IP ของ PC8? ช่วยบอก MAC ของคุณ"
```

ดังนั้นคำตอบข้อ 5 คือ **ARP Request ที่ส่งใน Ethernet Frame แบบ Broadcast**

## 4. Switch ได้รับ Broadcast แล้วส่งออกพอร์ตอื่น

ARP Request เข้าทางพอร์ต 1 จาก PC5:

```text
PC5 ── ARP Request ──▶ Switch
                         ├── พอร์ต 2 ──▶ PC6
                         ├── พอร์ต 3 ──▶ PC7
                         └── พอร์ต 4 ──▶ PC8
```

Switch ส่ง Broadcast ออก **ทุกพอร์ตยกเว้นพอร์ตที่รับเข้ามา**

- PC6 ได้รับ แต่ IP ที่ถามไม่ใช่ของตน → ไม่ตอบ
- PC7 ได้รับ แต่ IP ที่ถามไม่ใช่ของตน → ไม่ตอบ
- PC8 ได้รับ และเป็นเจ้าของ IP ที่ถาม → **ตอบด้วย ARP Reply**

**คำตอบข้อ 6:** PC6, PC7 และ PC8 ได้รับ (ผลเหมือน Hub: Broadcast ไปถึง PC อื่นทั้งหมด)

## 5. Switch รู้ทางกลับไป PC5 ได้อย่างไร ทั้งที่ตารางว่าง?

กลไกคือ: เมื่อ Switch รับ Frame มันเรียนรู้จาก **MAC ต้นทาง** และ **พอร์ตที่ Frame เข้ามา**

ตอน ARP Request จาก PC5 เข้าพอร์ต 1 Switch เห็นว่า MAC ต้นทาง = PC5 และเข้ามาทางพอร์ต 1 จึงจดไว้:

| MAC ของเครื่อง | อยู่ทางพอร์ต |
| -------------- | ------------ |
| PC5            | พอร์ต 1      |

Switch เรียนรู้ที่อยู่ของ **ผู้ส่ง** จาก MAC ต้นทาง ไม่ต้องรอให้ PC5 เป็นผู้รับก่อน
เมื่อ ARP Reply กลับมาภายหลัง ตารางจึงไม่ว่างแล้ว

## 6. PC8 ส่ง ARP Reply กลับ PC5 แบบ Unicast

```text
ARP Reply
  MAC ต้นทาง   = PC8
  MAC ปลายทาง = PC5
```

เมื่อ Reply เข้า Switch ทางพอร์ต 4 เกิดสองเรื่อง:

**เรื่องแรก: เรียนรู้ผู้ส่ง** → "MAC ของ PC8 อยู่ทางพอร์ต 4"

| MAC ของเครื่อง | อยู่ทางพอร์ต |
| -------------- | ------------ |
| PC5            | พอร์ต 1      |
| PC8            | พอร์ต 4      |

**เรื่องที่สอง: ดูว่าจะส่งไปไหน** → MAC ปลายทางคือ PC5 ตารางบอกว่าอยู่พอร์ต 1 จึงส่งออกเฉพาะพอร์ตนั้น

```text
PC8 ── ARP Reply ──▶ Switch ── พอร์ต 1 ──▶ PC5
                      (PC6 และ PC7 ไม่ได้รับ Reply นี้)
```

**คำตอบข้อ 7:** มีเพียง PC5 ได้รับ

เปรียบเทียบกับ Hub:

| อุปกรณ์            | เมื่อรับ ARP Reply ที่ส่งถึง PC5             |
| ------------------ | -------------------------------------------- |
| Hub                | ส่งสัญญาณออกพอร์ตอื่นทั้งหมด                 |
| Switch (ในขั้นนี้) | รู้พอร์ตของ PC5 แล้ว จึงส่งออกเฉพาะพอร์ตนั้น |

## 7. PC5 ส่ง ICMP Echo Request ไป PC8

หลังรับ ARP Reply สองอย่างช่วยกันคนละหน้าที่:

- **PC5** รู้ MAC ของ PC8 จาก ARP → เตรียม Frame "MAC ปลายทางคือ PC8"
- **Switch** รู้พอร์ตของ PC8 จาก Frame ที่ PC8 ส่งมา → ส่งต่อ "MAC ของ PC8 อยู่พอร์ต 4"

ข้อมูลของ ping:

```text
MAC ต้นทาง   = PC5        MAC ปลายทาง = PC8
IP ต้นทาง    = PC5        IP ปลายทาง  = PC8
ข้อความ      = ICMP Echo Request
```

```text
PC5 ── ICMP Echo Request ──▶ Switch ──▶ PC8
                               │
                         ไม่ส่งไป PC6 / PC7
```

**คำตอบข้อ 8:** มีเพียง PC8 ได้รับ

ต่างจาก Hub ตรงที่ PC6 และ PC7 ไม่ได้รับ Frame นี้ตั้งแต่แรก ไม่ใช่ "ได้รับแล้วค่อยทิ้ง" แบบตัวอย่าง Hub

## 8. แยกเหตุผล: ส่งตรง vs Collision Domain

| สิ่งที่เห็น                            | เหตุผล                                                                        |
| -------------------------------------- | ----------------------------------------------------------------------------- |
| Unicast ถูกส่งเฉพาะพอร์ตปลายทาง        | Switch ใช้ **MAC Address Table** เลือกพอร์ต                                   |
| แต่ละพอร์ตเป็น Collision Domain แยกกัน | Switch แยกการเชื่อมต่อของแต่ละพอร์ต ไม่ให้ทุกเครื่องใช้สื่อกลางร่วมกันแบบ Hub |

**อย่าจำว่า** "มีหลาย Collision Domain จึงรู้ว่าจะส่งถึง PC8" เพราะการเลือกพอร์ตของ PC8 ต้องอาศัยข้อมูลใน MAC Address Table

## 9. ARP กับ OSI (แก้ความสับสนจากคำอธิบายในวิดีโอ)

ในวิดีโอเรียก ARP ว่า packet และพูดถึงข้อมูลในส่วน Layer 3 แต่ **ARP ไม่ได้บรรจุอยู่ภายใน IPv4 Packet**

```text
ARP:
Ethernet Frame
└── ARP Message

Ping ในตัวอย่าง:
Ethernet Frame
└── IPv4 Packet
    └── ICMP Message
```

ค่า **EtherType `0x0806`** ใน Ethernet Frame บอกว่าเนื้อหาข้างในเป็น ARP ตอนดู PDU Details ใช้ค่านี้ยืนยันได้ว่า "นี่คือ ARP" โดยไม่ต้องสรุปว่า ARP เป็น IPv4 Packet

| ข้อ | สิ่งที่ถาม                  | คำตอบพร้อมเหตุผล                                       |
| --- | --------------------------- | ------------------------------------------------------ |
| 5   | สิ่งแรกที่ PC5 ส่งคืออะไร   | ARP Request แบบ Broadcast เพราะ ARP Cache ของ PC5 ว่าง |
| 6   | ใครได้รับ Request           | PC6, PC7, PC8 เพราะ Switch ส่ง Broadcast ออกพอร์ตอื่น  |
| 7   | ใครได้รับ ARP Reply         | PC5 เพราะ Switch เรียนรู้พอร์ตของ PC5 แล้ว             |
| 8   | ใครได้รับ ICMP Echo Request | PC8 เพราะ Switch เรียนรู้พอร์ตของ PC8 แล้ว             |

## 11. นับ Collision Domain

แต่ละพอร์ตแยกกัน ในภาพที่มี PC 4 เครื่องต่อ Switch โดยตรง:

```text
PC5 ───── Switch พอร์ต 1   ← Collision Domain 1
PC6 ───── Switch พอร์ต 2   ← Collision Domain 2
PC7 ───── Switch พอร์ต 3   ← Collision Domain 3
PC8 ───── Switch พอร์ต 4   ← Collision Domain 4
```

นับทีละ **การเชื่อมต่อที่ใช้งาน**: 4 เส้น = **4 Collision Domains**

- ไม่ได้นับหนึ่งวงสำหรับ PC แล้วบวกอีกหนึ่งวงสำหรับพอร์ต
- ไม่นับพอร์ตว่างที่ไม่ได้แสดงเป็นการเชื่อมต่อ
- **อย่าสรุปว่า 4 Collision Domains = 4 Broadcast Domains** เพราะ ARP Request ยังไปถึง PC อื่นทุกเครื่อง (ทั้งหมดอยู่ Broadcast Domain เดียวกัน)

## จดลง Notebook (สำหรับ CCNA)

- ARP Cache ของ PC: จับคู่ **IP ↔ MAC**
- MAC Address Table ของ Switch: จับคู่ **MAC ↔ พอร์ต**
- Switch เรียนรู้จาก **Source MAC** ของ Frame ที่รับเข้า
- Broadcast ถูกส่งออกพอร์ตอื่น ยกเว้นพอร์ตขาเข้า
- เมื่อรู้พอร์ตของ MAC ปลายทางแล้ว Switch ส่ง Unicast ออกเฉพาะพอร์ตนั้น
- แต่ละพอร์ตที่เชื่อมต่อเป็น Collision Domain แยกกัน
- EtherType `0x0806` = ARP

## Concept ที่ต้องเข้าใจ

```text
PC5 ส่ง ARP Request
    ↓
Switch เรียนรู้พอร์ตของ PC5
    ↓
PC8 ส่ง ARP Reply
    ↓
Switch เรียนรู้พอร์ตของ PC8 และส่ง Reply เฉพาะทาง PC5
    ↓
PC5 ส่ง ping
    ↓
Switch ส่งเฉพาะทาง PC8
```

"ตารางว่างตอนเริ่ม" ไม่ได้แปลว่า "ตารางยังว่างตอน Reply กลับมา"

แยกสามเรื่องนี้ให้ออก:

- PC ใช้ **ARP** หา MAC
- Switch ใช้ **ตาราง** หาพอร์ต
- **Collision Domain** บอกขอบเขตของการใช้สื่อกลางและการชนกัน

# ภาคผนวก: Tips แก้ปัญหา Network ทุกองค์กร

## `arp -a` ใช้แก้ปัญหา IP ชนได้อย่างไร

### 1. ARP คืออะไร

- **ARP (Address Resolution Protocol)** แปลง IP Address → MAC Address
- เครื่องเก็บข้อมูลนี้ไว้ใน **ARP Table**
- ถ้า IP เดียวกันแต่เจอ MAC มากกว่า 1 ตัว → มีโอกาส IP ชน

### 2. `arp -a` คืออะไร

คำสั่งดู ARP Table ทั้งหมดในเครื่อง

```text
arp -a
```

ตัวอย่างผลลัพธ์:

```text
Internet Address    Physical Address     Type
192.168.1.10        00-11-22-33-44-55    dynamic
192.168.1.20        aa-bb-cc-dd-ee-ff    dynamic
```

### 3. ใช้ `arp -a` ตรวจ IP ชนอย่างไร

กรณีสงสัยว่า IP ตัวเองชน:

1. ดู IP ตัวเอง: `ipconfig`
2. ดู ARP Table: `arp -a`
3. สังเกตว่า
   - IP ที่สงสัย **เปลี่ยน MAC ไปมา**
   - หรือ MAC **ไม่ตรงกับเครื่องจริง**

**อาการของ IP ชน**

- Ping ได้บ้าง ไม่ได้บ้าง
- ต่อเน็ตติด ๆ ดับ ๆ
- MAC Address เปลี่ยนทุกครั้งที่สั่ง `arp -a`

**ตัวอย่างสถานการณ์จริง** (IP `192.168.1.50`)

```text
ครั้งแรก:      192.168.1.50 → 00-11-22-33-44-55
ผ่านไปสักพัก:  192.168.1.50 → aa-bb-cc-dd-ee-ff
```

IP เดียวแต่ MAC ไม่เหมือนกัน → **น่าสงสัยว่า IP ชน**

> **หมายเหตุเพิ่มเติม:** ต้นฉบับสรุปว่า "ชนแน่นอน" ซึ่งแรงเกินไป MAC ของ IP เดียวกันเปลี่ยนได้จากสาเหตุอื่นด้วย เช่น เปลี่ยนเครื่องแล้ว DHCP แจก IP เดิมให้เครื่องใหม่ หรือ ARP Spoofing ควรยืนยันด้วยข้อ 5 ก่อนสรุป

### 4. หา "ตัวที่ชน" ว่าเป็นเครื่องไหน

1. จด MAC Address ที่ชน
2. เอา MAC ไปเช็กที่
   - **Switch** (MAC Address Table) → ได้ว่าอยู่พอร์ตไหน
   - **DHCP Server**
   - **Router**
3. จะรู้ว่า MAC นี้มาจากพอร์ตไหน / เครื่องไหน

(ตรงนี้เชื่อมกับเนื้อหา Lab: ใช้ `show mac address-table` บน Switch หาพอร์ตของ MAC นั้นได้)

### 5. ล้าง ARP เพื่อยืนยันปัญหา

ARP เก่าอาจหลอกเราได้ ให้ล้างแล้วตรวจซ้ำ

```text
arp -d *
ping <IP ที่ชน>
arp -a
```

ถ้า MAC เปลี่ยนอีก → ยืนยันว่า IP ชนจริง (บน Windows ต้องเปิด Command Prompt แบบ Administrator ถึงจะล้างได้)
